# SLIs and SLO Groundwork Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Record the four SLIs of ml-api and backend-api as Sloth-generated `VMRule`s, evaluated by vmalert, with the windows the SRE workbook's alerting needs.

**Architecture:** Each app keeps its SLIs in `apps/base/<app>/slo.yaml`. `scripts/slo-generate.sh` (everything shared: Sloth version, 28d period, MetricsQL validation, SLI rules only) runs Sloth from its pinned image and writes `apps/base/<app>/slo-rules.yaml`, a `VMRule` that Flux applies with the app. vmalert, switched on in the existing chart, evaluates the rules into VMSingle. ml-api's availability comes from a new `VMProbe` that sends `POST /predict` through the existing blackbox exporter.

**Tech Stack:** Sloth v0.16.0 (`ghcr.io/slok/sloth:v0.16.0`, run with Docker), `victoria-metrics-k8s-stack` 0.93.0 (vmalert), `prometheus-blackbox-exporter` 11.19.1, Flux v2.9.5, bash.

**Spec:** [SLIs and SLO groundwork](../specs/2026-09-26-slo-sli-design.md)

## Global Constraints

- Sloth runs only on a developer machine from `ghcr.io/slok/sloth:v0.16.0`: `--default-slo-period=28d --disable-default-slo-plugins`, plugins `sloth.dev/contrib/validate_victoria_metrics/v1` then `sloth.dev/core/sli_rules/v1`. No alert rules.
- Every SLO has `objective: 99.9` as a placeholder and an `alerting.name` (Sloth rejects an SLO without one). Thresholds: `/process` `le="0.25"`, `/predict` `le="1.0"`, exactly as exported.
- Generated `VMRule` is `<folder>-slo` in the namespace named like the folder. `slo.yaml` is not listed in `kustomization.yaml`; `slo-rules.yaml` is.
- vmalert on with `notifier.blackhole: "true"`; Alertmanager stays off.
- VMSingle `retentionPeriod: "30d"`. `base` drops its `5Gi` request (chart default `20Gi`, sized for about 15 GB); devops-cs keeps `5Gi` through an overlay patch because `local-path` can't grow its existing volume.
- No application code changes. Failure tests are throwaway, run with Flux suspended and reverted.
- Push only after the user approves it. Flux reads GitHub, so cluster checks (Task 3) start after the push.

## Review Focus

1. A query that matches nothing (`le="1"`, a wrong job) gives no SLI series instead of a wrong value. Task 3 Step 3 expects exactly 4 series with values.
2. A healthy backend has no 5xx series; without `or vector(0)` `process-availability` would be missing. Task 3 Step 3 expects it present and 0.
3. vmalert ignores the `VMRule`s in the app namespaces. Task 3 Step 2 expects 32 rules loaded, none with errors.
4. `slo-rules.yaml` goes stale after a `slo.yaml` edit. Task 2 Step 6 exercises it.
5. devops-cs's PVC request changes and the operator tries to resize a volume `local-path` can't grow. Task 1 Step 3 and Task 3 Step 2 expect `5Gi` on devops-cs.

- [ ] **Step 1: Write the generator**

`scripts/slo-generate.sh` (then `chmod +x scripts/slo-generate.sh`):

```bash
#!/usr/bin/env bash
# Generates apps/base/<app>/slo-rules.yaml (a VMRule) from apps/base/<app>/slo.yaml
# with Sloth. Everything shared by all apps' SLOs is set here: Sloth version,
# 28-day SLO period, MetricsQL validation, and SLI recording rules only.
# Drift check: scripts/slo-generate.sh && git diff --exit-code -- 'apps/base/*/slo-rules.yaml'
set -euo pipefail
cd "$(dirname "$0")/.."

for spec in apps/base/*/slo.yaml; do
  dir=$(dirname "$spec")
  app=$(basename "$dir") # the folder name is also the namespace
  # The spec goes in on stdin: a bind mount can miss a file an editor just replaced.
  rules=$(docker run --rm --interactive ghcr.io/slok/sloth:v0.16.0 generate \
    -i /dev/stdin \
    --default-slo-period=28d \
    --disable-default-slo-plugins \
    -s '{"id":"sloth.dev/contrib/validate_victoria_metrics/v1"}' \
    -s '{"id":"sloth.dev/core/sli_rules/v1"}' <"$spec")
  {
    echo "# Generated by scripts/slo-generate.sh from slo.yaml. Do not edit."
    echo "apiVersion: operator.victoriametrics.com/v1beta1"
    echo "kind: VMRule"
    echo "metadata:"
    echo "  name: $app-slo"
    echo "  namespace: $app"
    echo "spec:"
    sed -e '/^#/d' -e '/^---$/d' -e '/^$/d' -e 's/^/  /' <<<"$rules"
  } >"$dir/slo-rules.yaml"
  echo "wrote $dir/slo-rules.yaml"
done
```

- [ ] **Step 2: Write the SLI specs**

`apps/base/backend-api/slo.yaml`:

```yaml
# SLIs of backend-api for Sloth. Not a Kubernetes object: not in kustomization.yaml.
# After editing, run scripts/slo-generate.sh and commit both files.
version: prometheus/v1
service: backend-api
slos:
  - name: process-availability
    alerting:
      name: BackendApiProcessAvailability # used once alert rules are generated
    objective: 99.9 # placeholder, required by Sloth; unused until targets are set
    sli:
      events:
        error_query: sum(rate(backend_api_requests_total{endpoint="/process",status=~"5.."}[{{.window}}])) or vector(0)
        total_query: sum(rate(backend_api_requests_total{endpoint="/process"}[{{.window}}]))
  - name: process-latency
    alerting:
      name: BackendApiProcessLatency # used once alert rules are generated
    objective: 99.9 # placeholder, required by Sloth; unused until targets are set
    sli:
      events:
        error_query: |
          sum(rate(backend_api_request_duration_seconds_count{endpoint="/process"}[{{.window}}]))
          - sum(rate(backend_api_request_duration_seconds_bucket{endpoint="/process",le="0.25"}[{{.window}}]))
        total_query: sum(rate(backend_api_request_duration_seconds_count{endpoint="/process"}[{{.window}}]))
```

`apps/base/ml-api/slo.yaml`:

```yaml
# SLIs of ml-api for Sloth. Not a Kubernetes object: not in kustomization.yaml.
# After editing, run scripts/slo-generate.sh and commit both files.
version: prometheus/v1
service: ml-api
slos:
  - name: predict-availability
    alerting:
      name: MlApiPredictAvailability # used once alert rules are generated
    objective: 99.9 # placeholder, required by Sloth; unused until targets are set
    sli:
      events:
        error_query: |
          sum(count_over_time(probe_success{job="probe/ml-api/predict"}[{{.window}}]))
          - sum(sum_over_time(probe_success{job="probe/ml-api/predict"}[{{.window}}]))
        total_query: sum(count_over_time(probe_success{job="probe/ml-api/predict"}[{{.window}}]))
  - name: predict-latency
    alerting:
      name: MlApiPredictLatency # used once alert rules are generated
    objective: 99.9 # placeholder, required by Sloth; unused until targets are set
    sli:
      events:
        error_query: |
          sum(rate(ml_api_request_duration_seconds_count{endpoint="/predict"}[{{.window}}]))
          - sum(rate(ml_api_request_duration_seconds_bucket{endpoint="/predict",le="1.0"}[{{.window}}]))
        total_query: sum(rate(ml_api_request_duration_seconds_count{endpoint="/predict"}[{{.window}}]))
```

- [ ] **Step 3: Write the probe**

`apps/base/ml-api/vmprobe.yaml`:

```yaml
# Black-box source of the predict-availability SLI (slo.yaml): a synthetic
# POST /predict every 30 s through the shared blackbox exporter. ml-api's own
# counters only ever record status 200, so they can't show its failures.
apiVersion: operator.victoriametrics.com/v1beta1
kind: VMProbe
metadata:
  name: predict
  namespace: ml-api
spec:
  vmProberSpec:
    url: prometheus-blackbox-exporter.monitoring.svc.cluster.local:9115
  module: http_post_2xx
  interval: 30s
  targets:
    staticConfig:
      targets:
        - http://ml-api.ml-api.svc.cluster.local:8000/predict
```
